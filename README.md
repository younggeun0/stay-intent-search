# 숙소 찾기

어반스테이 소프트웨어 엔지니어 채용 과제. "운영/예약/숙박 도메인의 문제를 가정하고 작은 결과물을 제출한다"는 요구에 대해, **필터로 표현되지 않는 고객의 조건을 자연어로 받아 검색하는 프로토타입**을 만들었다.

- 배포: https://stay-intent-search.vercel.app/
- 작업 기간: 2026-10-12(월) 저녁 ~ 2026-10-13(화). 마감은 10/16(금) 24:00. (제출 시 확정)
- 방향 문서: [`docs/direction.md`](docs/direction.md) · AI 활용·검토 기록: [`docs/ai-log.md`](docs/ai-log.md) · 평가셋: [`eval/`](eval/)

> 공식 서비스가 아니다. 지점·객실 정보는 공개 사이트에서 수집했지만 **재고는 가짜 데이터**이고 가격은 하루치 조회값이다. 사진과 브랜드 심볼은 공식 CDN을 참조만 하고 파일을 복사하지 않았다.

## 1. 문제 정의

**가설:** 숙소 검색 필터(지역, 날짜, 인원)로 표현되지 않는 조건이 있고, 이런 조건은 고객센터 문의나 이탈로 이어진다.

공개 사이트(urbanstay.co.kr)를 관찰해 전제를 확인했다(`docs/direction.md` 3장, 스크린샷 `docs/evidence/`).

| 관찰 | 의미 |
|---|---|
| 검색 입력은 지역(8개 시도), 날짜, 인원뿐이고 결과에 필터·정렬이 없다 | "욕조", "침대 따로", "반려동물"은 검색할 수 없다 |
| 객실 상세 창에는 침실 수, 침대 구성, 욕실 수, 시설 태그가 **정형 데이터**로 있다 | 데이터는 있는데 검색에 쓰이지 않는다. 구현 비용이 낮은 개선 여지다 |
| 전망, 펫, 스파, 욕조, 트윈 같은 속성은 **객실 이름에만** 있다 | 이름에서 파생해야 한다 |
| 펫 가능 여부, 영유아 인원 기준은 지점 정책 아코디언 안의 텍스트뿐이다 | 고객이 직접 찾기 어렵다 |

고객이 직접 쓴 문장 5건을 받아 보니 4건이 "연말에", "11월 말 주말 포함 3일"처럼 **정확한 날짜 대신 기간**을 말했다. 사이트는 체크인·체크아웃을 요구하므로 고객이 날짜를 바꿔 가며 반복 검색해야 한다. 이것을 두 번째 축으로 삼았다.

**가정으로 남긴 것:** 내부 데이터(문의량, 이탈률)가 없으므로 "문의와 이탈로 이어진다"는 부분은 검증하지 못했다. 면접에서 확인할 질문으로 적어 두었다(`direction.md` 10장).

## 2. 무엇을 만들었나

```
자연어 (여러 턴 대화) → LLM이 검색 조건 JSON 추출 → 코드가 정규화 → 코드가 목업 인벤토리 검색 → 결과·대안 제시 → 고객 확인
```

- **조건 추출**: 지역·동네, 특정 날짜 또는 기간(범위, 박수, 주말 포함), 인원·영유아, 반려동물, 오션뷰, 침실·침대 수, 객실 특성(욕조, 스파, 트윈, 베리어프리, 복층, 커넥팅), 시설(주방, 세탁기, 식기세척기, 책상, 스타일러). 표현할 수 없는 조건("주차 무료", "조용한 곳")은 버리지 않고 `unhandled`로 남겨 화면에 보여 준다.
- **되묻기**: 날짜와 인원이 없으면 묻는다. 대화 전체를 매 턴 다시 추출하므로 "4명이요"처럼 일부만 답해도 이어진다.
- **기간 검색**: "11월 말 주말 포함 2박"이면 11/21~30 안에서 토요일 밤을 포함하는 모든 체크인 일정을 펼쳐 빈 객실을 찾는다.
- **헬프 센터 연결**: 검색 조건으로 못 쓰는 문의("주차 무료", "조식")는 헬프 센터 검색 링크로, 0건 이유가 정책(반려동물, 최대 인원)에서 오면 해당 FAQ 아티클로, 상세 창에서는 지점 이용 안내 카테고리로 보낸다. 아티클이 있다고 확인한 키워드에만 링크를 건다.
- **결과 0건이면 이유와 최소 변경 조합**: 조건을 넓은 것부터 적용하며 남는 객실 수를 세고, 결과가 나오는 최소 조건 조합(최대 3개)을 버튼으로 낸다. 예: "강아지랑 이번 주말 속초 오션뷰" → ① 반려동물 제외(12실) ② 반려동물을 유지하려면 다른 날짜 + 다른 지역 + 오션뷰 제외(2실, 펫 객실은 시흥에 둘뿐이고 오션뷰가 아니며 이번 주말은 예약이 찼음).
- **대화 UI**: 공식 사이트의 색·모서리·컴포넌트 형태를 따르되 PC 2단으로 반응형(`DESIGN.md`). 조건 칩 ×나 대안 버튼을 누르면 짧은 고객 발화("오션뷰가 아니어도 괜찮아요")로 대화에 남기고 그 자리에서 다시 검색한다. 날짜 범위 선택 시트는 공식 사이트 동작을 따랐다. 시스템 글꼴 200%에서도 깨지지 않게 rem 기준으로 맞췄다.
- **인벤토리**: 공개 사이트의 30개 지점 187개 객실 유형. 페이지가 호출하는 공개 API에서 인원, 면적, 침실·침대·욕실, 시설 아이콘(주방·세탁기·식기세척기·책상·스타일러·욕조·휠체어·복층·펫·커넥팅), 사진을 받아 `src/data/official.json`에 두었다. 전망·스파·트윈처럼 이름에만 있는 속성은 이름에서 파생한다. 가격은 2026-12-02 1박 조회값이고 날짜별 재고는 가짜다.

## 3. 범위 판단

**포함:** 조건 추출, 검색, 되묻기, 0건 대안, 확인 단계까지의 대화 UI, 평가셋과 평가 스크립트, 배포.

**의도적으로 뺀 것**

| 항목 | 이유 |
|---|---|
| 결제, 예약 확정, 인증 | "예약 확정 직전에 멈춘다"가 설계 원칙. 재고를 가진 PMS 없이 확정을 흉내 내면 가짜 기능이 된다 |
| 실제 PMS·채널 매니저 연동 | 접근 불가. 대신 교체 지점을 코드로 분리했다(아래 6장) |
| 멀티모달(이미지 입력) | 처음 아이디어였으나, 꼭 필요한 실제 상황을 찾지 못했다. 텍스트 조건이 문제의 본질이다 |
| 다국어 | 평가셋을 한국어로만 만들 수 있었다 |
| Spring API 분리 | 서버 엔드포인트가 하나(`interpret`)뿐이라 Next.js 서버 함수로 충분했다. 분리는 과제 범위 밖 |
| 벡터 검색 | 펫, 인원, 재고처럼 정확히 맞아야 하는 조건에 유사도 검색을 쓰면 오답이 클레임이 된다. 정책 질의응답과 분위기 순위에만 맞는다(6장) |

## 4. 설계 결정

1. **LLM은 조건 추출만 한다.** 객실, 재고, 가격, 답변 문장, 0건 이유는 모두 코드가 만든다. LLM이 쓰면 없는 객실이나 재고를 말할 수 있다.
2. **결정적으로 정할 수 있는 것은 코드가 정한다.** 되묻기 여부, 날짜가 정해졌을 때 기간 필드 비우기, `0`/`false`를 `null`로 통일. 처음에는 모델에게 맡겼는데 과잉 되묻기가 31건 나왔다(v1). 코드로 옮기자 0건이 됐다(v2).
3. **해석 규칙은 한 곳(`src/lib/rules.ts`)에 둔다.** LLM 프롬프트이자 정답 라벨의 기준이다. 규칙을 바꾸면 라벨을 다시 검수한다.
4. **매 턴 대화 전체를 다시 추출한다.** 이전 결과를 합치는 상태가 없어 구현과 평가가 단순하다. 화면 조작(칩 ×, 대안 버튼)도 고객 발화로 대화에 남겨 같은 경로를 탄다. 그 문구가 다음 추출에서 의도대로 해석되는지 실제 모델로 검사한다(`npm run eval:roundtrip`, 14/14).
5. **인원 규칙:** 36개월 이하 영유아는 인원에 넣지 않는다(공식 정책). 토퍼는 침대로 세지 않는다. "강아지랑 둘이"는 1명이다.
6. **인원 조건은 대안으로 풀지 않는다.** 못 묵는 방을 권할 수 없다.
7. **안전장치:** 서버 함수는 공개 POST로 호출될 수 있어 Zod로 검증하고 크기를 제한한다(턴 20개, 턴당 300자). 기준일은 서버에서 KST로 계산한다. AI Gateway 지출 한도 $10.

## 5. 평가

**구현보다 평가셋을 먼저 만들었다.** 55건(dev 37, holdout 18). AI가 초안을 쓰고 사람이 전부 검수했다. holdout에는 사용자가 dev를 보지 않고 직접 쓴 5건이 포함된다. 프롬프트는 dev 실패만 보고 고쳤고, holdout은 마지막에 한 번만 측정했다.

채점은 필드별 정확 일치. 케이스 정답률은 모든 필드가 맞은 비율이다. 되묻기 오류는 "물어야 할 때 안 물음"과 "안 물어도 될 때 물음"을 따로 센다.

| 버전 | 바뀐 것 | 모델 | dev 정답 | 되묻기 오류 |
|---|---|---|---|---|
| v1 | 첫 프롬프트 | gemini-2.5-flash-lite | 16/37 | 0 |
| v1 | | gpt-4.1-nano | 2/37 | 31 |
| v2 | 되묻기·정규화를 코드로, 달력 제공, 대화록 입력 | gemini-2.5-flash-lite | 18/37 | 0 |
| v2 | | gpt-4.1-nano | 13/37 | 2 |
| v2 | 유료 등급 | **gpt-6-luna** | **35/37** (필드 100%) | 0 |
| v2 | | claude-haiku-5.5 | 33/37 | 0 |

**모델 선택:** 저가 모델 세 개의 단가가 같아($0.10/$0.40~0.50 per 1M tokens) 가격이 아니라 측정으로 골랐다. Luna와 Haiku의 2건 차이는 실행마다 흔들리는 폭(Gemini는 4건) 안이라 정확도로 가르지 못했고, 비용(Luna 0.6배)과 p95 지연(2.8s vs 3.7s)으로 Luna를 택했다. 평가셋 1회 비용은 약 $0.013.

**holdout (마지막 1회, gpt-6-luna, 18건):** 케이스 정답 **14/18 (78%)**, 필드 정답 98%, 되묻기 오류 1건, p95 2.8s. dev(95%)보다 낮다. 오답 4건은 모두 "이 표현을 어떻게 해석하느냐"의 경계에 있는 것들이다.

| 케이스 | 입력 | 라벨 | 모델 |
|---|---|---|---|
| h02 | "강아지랑 둘이" | 1명 (사람만 셈) | 2명 |
| h04 | "11월 중에" | 11/1~30 | 11/11~20 ("중순"으로 읽음) |
| h09 | "장기 투숙 가능한 곳 … 30박" | unhandled 없음 (30박이 표현) | unhandled에 "장기 투숙 가능한 곳" |
| u04 | "세 커플" | 6명 | 인원 되묻기 |

이 결과를 보고 프롬프트를 고치지 않았다. h02·h09는 dev에서도 같은 유형이 보였던 것이고(m06, d07), h04·u04는 holdout에서 처음 드러난 빈틈이다. 규칙(`rules.ts`)에 "N월 중" = 한 달 전체, "N커플" = 2N명이 이미 적혀 있는데도 틀렸으므로, 다음 개선은 프롬프트 표현이 아니라 이런 경계 표현을 dev 케이스로 더 넣는 것이다.

**남은 오답 유형:** 인원 해석. "돌 지난 아기 하나"를 인원에 포함(d03), "아이 둘이라 침대 따로"를 침대 4개로 읽음(d06). 둘 다 문장이 애매하고, 확인 단계에서 고객이 칩을 보고 고칠 수 있어 라벨은 규칙대로 두었다.

**한계로 적어 두는 것:** 기간 검색 규칙은 사람이 쓴 holdout을 보고 만들었다. 모델 결과를 보고 고친 것은 아니지만, 그 5건의 점수는 완전히 처음 보는 입력보다 유리할 수 있다.

## 6. 한계와 다음 단계

- **가짜 재고·가격.** 실제 서비스에서는 PMS 재고 API로 바꾼다. LLM이 만드는 조건 JSON은 그대로 두고 `src/lib/search.ts`의 데이터 소스만 바꾸는 구조다.
  ```
  자연어 → 조건 JSON → [지금] 목업 배열 필터
                     → [PMS 연동 후] DB 쿼리 + PMS 재고/요금 API
  ```
- **문의·이탈 가설 검증.** 채널톡 문의 로그에서 "조건 확인" 유형의 비율을 보면 된다.
- **unhandled 조건의 처리.** "주차 무료", "조식"은 헬프 센터 검색 링크로 보내고, "조용한 곳"처럼 아티클이 없는 조건은 글자로만 둔다. 헬프 센터의 지점별 아티클 약 300편에 RAG를 붙이면 정책 질의응답으로, 리뷰 유사도를 붙이면 분위기 순위로 확장할 수 있다(하이브리드). 주 검색은 정형 필터를 유지한다.
- **모델 흔들림.** 같은 입력에 실행마다 1~2건이 바뀐다. 운영에서는 실패 로그를 평가셋에 되먹이는 순환이 필요하다.
- **평가셋 크기.** 55건은 유형을 덮는 데는 충분하지만 통계적으로는 작다.

## 7. AI 활용과 검토

Claude Code로 설계·구현·문서를 진행했고, 제안을 채택·수정·반려한 기록을 [`docs/ai-log.md`](docs/ai-log.md)에 날짜별로 남겼다. 대표적인 것:

- AI가 운영 쪽 과제(청소 사진 검수)를 추천했으나, 평가셋을 만들 수 없다는 이유로 **반려**하고 대화형 예약을 택했다.
- AI가 "객실 속성은 이름에만 있다"고 결론 내렸는데, 상세 창을 열어보지 않은 일반화였다. 사람이 **정정**했고, 그 결과 인벤토리를 정형 사양과 이름 기반 속성의 두 층으로 설계했다.
- AI가 "결제 수단을 등록하지 말라"고 안내했는데 틀린 조언이었다. 실제 호출로 무료 등급의 모델 범위를 확인해 **정정**했다.
- 프롬프트 예시가 holdout 문장과 겹치는 것을 발견해 예시를 바꿨다.
- 라벨 55건은 AI가 규칙과 대조해 초안 검토를 하고, 판단이 갈리는 3건만 사람이 결정했다.

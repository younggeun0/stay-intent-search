# AI 활용 및 검토 기록

> 과제 평가 항목인 "AI 활용 및 검토 과정"의 근거 자료다. AI의 제안을 **채택, 수정, 반려**한 내용과 그 이유를 남긴다.

## 2026-10-13 · 방향 설정 (Claude Code)

- **AI 제안:** 처음 아이디어(멀티모달 AI 예약 웹앱)가 공고의 운영 중심 업무와 맞지 않는다고 지적하고, 운영 쪽 후보(청소 사진 검수, 문의 티켓화)를 추천했다.
- **내 검토:** 내부 PMS를 모르는 상태에서 운영 문제를 가정하면 근거가 약하다. 청소 사진 안은 성공/실패 기준에 맞는 샘플 이미지를 구하기 어려워 평가가 불가능하다고 판단했다.
- **결과:** 추천을 반려하고 대화형 예약(C안)을 채택했다. AI도 같은 근거로 C안이 낫다고 재판단했다. 대신 "AI는 의도 해석만, 재고·가격은 결정적 로직", "평가셋 선작성", "멀티모달은 필요할 때만"이라는 조건을 받아들였다.

## 2026-10-13 · 공개 사이트 근거 수집 (Claude Code + 브라우저 자동화)

- **AI 작업:** 브라우저로 홈 검색, 검색 결과, 지점 상세를 확인하고 스크린샷을 `docs/evidence/`에 저장했다.
- **검토 포인트:** 객실 속성이 이름에만 있다는 판단은 홈 큐레이션 목록 텍스트에서 나왔다. 모든 지점을 확인한 것은 아니므로 "관찰한 범위에서"라는 단서를 달았다. 내부 API 응답은 과제 근거로 쓰지 않기로 했다(공개 UI로 충분하고, 비공개 구조에 기대지 않기 위해).

## 2026-10-13 · AI 관찰 오류 정정 (사람 검토)

- **AI 판단:** "오션뷰, 펫룸 등 객실 속성은 객실 이름에만 있다"고 결론 내렸다.
- **내 검토:** 객실 카드의 `자세히 보기` 창에 더 많은 정보가 있다고 지적했다.
- **확인 결과:** AI가 상세 창을 열어보지 않고 일반화한 것이었다. 실제로 상세 창에는 인원, 크기, 침실 수, 침대 구성, 욕실 수, 시설 태그가 정형 데이터로 있었다. 전망, 펫, 욕조 등은 여전히 이름에만 있었다.
- **반영:** 관찰 표를 3a(정형 사양)/3b(이름에만 있는 속성)/3c(둘 다 검색 불가)로 고쳤다. 목업 인벤토리를 두 층으로 설계하도록 바꿨다. "데이터는 있는데 검색에 안 쓰인다"는 점은 가설을 오히려 강화했다.
- **교훈:** AI가 화면을 일부만 보고 내린 "~에만 있다"는 결론은 직접 확인한다.

## 2026-10-13 · 평가셋과 인벤토리 설계 (Claude Code + 리뷰 모델 조언)

- **조언 채택:** 구현 전에 별도 리뷰 모델에게 작업 순서를 검토받았다. 다음을 채택했다.
  - 스키마 → 해석 규칙 → 평가셋 → 인벤토리 순서
  - **dev/holdout 분리:** 프롬프트를 dev로만 고치고 holdout은 마지막에 한 번만 측정한다. "v1 72% → v2 91%"가 dev 과적합인지 구분하기 위해서다.
  - **정답 라벨은 사람이 검수:** AI가 입력, 정답, 추출을 모두 만들면 검증이 순환 구조가 된다.
- **AI가 라벨 실수를 기계적으로 잡게 한 장치:** 해석 규칙에서 나오는 불변식(날짜 없음 ⇔ 날짜 되묻기, 체크아웃 > 체크인 등)을 `eval/check.ts`로 검사하고, 사람 검수용으로 요일을 함께 출력한다.
- **케이스를 쓰다 규칙의 빈틈을 발견:** "오늘/내일", 운영하지 않는 지역("경주"), "강아지랑 둘이"(사람 1명), 랜드마크("부산역 근처")는 처음 규칙에 없었다. 라벨을 추측으로 매기지 않고 규칙을 먼저 보강했다.
- **스크래핑 중단:** 브라우저 자동화로 지점 URL을 모으다 두 번 연속 실패했다(뒤로 가기 이탈, 렌더러 응답 없음). 미리 정한 1시간 제한에 따라 중단하고, 이미 관찰한 실제 지점명·객실명·인원과 상세 사양 2건을 바탕으로 직접 작성했다. 사양마다 `specSource`(observed/capacity/estimated)를 달아 추정값을 구분했다.

## 2026-10-13 · 확장 방향 검토

- **질문:** PMS에 접근할 수 있다면 벡터DB로 검색을 확장할 수 있는가?
- **AI 답변과 채택:** 주 검색은 정형 필터와 PMS 재고 API가 맞고, 벡터 검색은 정책 질의응답과 분위기 순위에만 쓰는 하이브리드 구조를 제안했다. 정확히 맞아야 하는 조건(펫, 인원, 재고)에 유사도 검색을 쓰면 오답이 클레임으로 이어진다는 근거에 동의해 채택했다. `direction.md` 10장에 기록했다.

## 2026-10-13 · 사람이 작성한 holdout 5건 추가

- **입력:** u01~u05는 사용자가 dev 케이스를 보지 않고 직접 쓴 문장이다. 정답 라벨은 AI가 해석 규칙대로 초안을 쓰고 사용자가 확인한다.
- **발견:** 5건 중 4건이 "연말", "11월 말", "12월 초", "11월에"처럼 **기간으로 날짜를 말했다.** AI가 쓴 dev 케이스는 대부분 날짜가 특정되어 있었다. 현재 규칙으로는 모두 "날짜 되묻기"가 정답이고, "예약 가능한 숙소들을 보여주세요"라는 요청 의도(기간 안의 빈 방 탐색)를 처리하지 못한다. AI가 만든 평가셋만으로는 드러나지 않았을 빈틈이다.
- **결정 (사용자):** 기간 검색을 지원하기로 했다(B안). 스키마에 `dateRange`, `nights`, `weekend`를 추가하고 기간 해석 규칙("N월 말" = 21일~말일, "연말" = 12/21~31, "3일" = 2박 등)을 정했다. u04 "세 커플"은 방 3개로 보기로 했고, "N팀이면 방 N개" 규칙으로 일반화했다.
- **영향받은 라벨:** d05·h04(기간), d07(30박 + 날짜 되묻기), d18("11월 첫째주 주말" → 첫 토요일 규칙으로 11/7), d24("두 가족" → 방 2개), h09(장기 투숙이 `nights`로 표현되어 `unhandled`에서 제거해 d07과 일관성 맞춤), u01~u05.

## 2026-10-13 · 여러 턴 케이스 추가

- **결정 (사용자):** 매 턴마다 대화 전체에서 조건을 다시 추출하는 방식에 동의했다. 이전 결과를 합치는 상태가 없어서 구현과 평가가 단순하다.
- **추가:** m01~m10(dev 7, holdout 3). 사용자가 요청한 "인원만 답함"(m01), "장소만 답함"(m02, m09)과 함께 날짜 답변, 조건 변경(m04, m10), 조건 추가(m05), 조건 취소(m06)를 넣었다.
- **규칙 추가:** 나중 말이 앞의 말을 덮는다, 취소하면 `null`, 일부만 답하면 나머지는 계속 되묻는다, AI 턴은 근거로 쓰지 않는다.

## 2026-10-13 · LLM 제공자 선택

- **AI 첫 제안:** Claude Opus 5.5 기준으로 "평가셋 1회 약 $1, 비용 걱정 없음"이라고 했다.
- **내 검토:** 그것도 비싸다고 판단했다. Jev를 포함해 웹 검색으로 성능과 가격을 다시 비교하게 했다.
- **결과:**
  - Jev(TypeSafe AI, 입력 $0.042/100만 토큰, 출력 무료)는 **제외**했다. 출력이 예/아니오·선택지·점수의 확률값뿐이라 JSON 추출이 안 되고, 공식 문서에 날짜와 숫자에 약하다고 적혀 있다. 이번 과제의 핵심이 날짜·인원 추출이라 정확히 약점에 해당한다.
  - 저가 모델 세 개(Claude Haiku 5.5, GPT-6 Luna, Gemini 2.5 Flash-Lite)는 가격이 거의 같다($0.10/$0.40~0.50). 한국어 구조화 추출을 비교한 공개 벤치마크는 찾지 못했다. 그래서 **가격이 아니라 평가셋 측정으로** 고르기로 했다.
  - Vercel AI Gateway의 월 $5 무료 크레딧을 쓴다. 키 하나로 세 회사 모델을 호출할 수 있고 평가셋 1회는 모델당 약 $0.03이다. 모델 ID와 가격은 Gateway의 `/v1/models`에서 직접 확인했다.

## 2026-10-13 · 프롬프트 작성 중 holdout 누출 발견

- **발견:** 해석 규칙을 프롬프트로 옮기다 보니 규칙의 예시 일부가 holdout 문장과 거의 같았다("강아지랑 둘이" = h02, "세 커플" = u04). 그대로 넣으면 holdout이 정답을 미리 본 셈이 된다.
- **조치:** 규칙은 `src/lib/rules.ts` 한 곳으로 모으고, 예시를 평가셋과 겹치지 않는 표현으로 바꿨다("고양이 데리고 혼자", "네 가족이 함께").
- **남는 한계:** 기간 검색 규칙은 사람이 쓴 holdout(u01~u05)을 보고 만들었다. 이것은 "이 표현을 어떻게 해석해야 맞는가"를 사람이 정한 **명세 변경**이고, 모델 결과를 보고 고친 **프롬프트 튜닝**과는 다르다. 그래도 u01~u05의 수치는 완전히 처음 보는 입력에 대한 점수보다 유리할 수 있다는 점을 결과 보고에 함께 적는다.

## 2026-10-13 · 첫 평가 실행 (v0 → v1 → v2)

- **v0 (실패):** AI Gateway 무료 크레딧은 카드 등록이 있어야 쓸 수 있었다. AI는 앞서 "결제 수단을 등록하지 말라"고 안내했는데, 커뮤니티 글 하나를 근거로 한 **틀린 조언**이었다. 등록 후에는 **무료 등급이 일부 모델만 허용**한다는 것이 드러났다. 짧은 호출로 직접 확인해 보니 Claude 전 모델, GPT-6 Luna, Gemini 3.x는 막혀 있었고 gpt-5-nano, gpt-4.1-nano, gemini-2.5-flash-lite만 가능했다. 문서의 무료 모델 목록 페이지로는 확정할 수 없어서 실제 호출로 확인했다.
- **v0에서 얻은 것:** Gemini가 돌아간 29건 중 25건이 `nights` 하나만 틀렸다. "날짜가 정해지면 박수는 비운다"는 내 규칙이 모델에게 부자연스러웠다. 모델에게 외우게 하는 대신 **코드가 정규화**하게 바꿨다.
- **v1 결과 (dev 37건):** gemini-2.5-flash-lite 16/37(필드 90%), gpt-4.1-nano 2/37(필드 82%, 과잉 되묻기 31건), gpt-5-nano는 "추론 없음"을 지원하지 않아 전부 거부.
- **v1 오답 분석 → v2 수정 (모두 dev 실패만 근거):**
  - **되묻기를 코드가 계산:** 되묻기 여부는 규칙상 추출 결과(날짜·기간·인원 유무)에서 결정된다. 모델이 판단할 이유가 없었다.
  - **없음 표현 통일:** `0`/`false`를 `null`로, region과 같은 area를 제거. 검색 의미가 같은 표현 차이로 오답 처리되지 않게 했다.
  - **달력 제공:** "다음주"를 이번 주로 계산하는 오류(d11, d29, m06). 요일 계산 대신 14주 달력에서 찾게 했다.
  - **대화록으로 입력:** 메시지 배열로 주면 앞 대화를 잊었다(m05에서 속초·날짜가 사라짐). 하나의 대화록으로 바꿨다.
  - **규칙 보강:** 이미 다른 필드로 표현한 조건을 `unhandled`에 중복으로 넣지 않게 했다.
- **설계 원칙 강화:** "AI는 해석, 코드는 정규화와 결정." 결정적으로 정할 수 있는 것(되묻기, 표현 통일, 요일)은 모델에게 맡기지 않는다. 정답 라벨 55건이 모두 정규화의 고정점인지 `eval:check`로 검사한다.
- **v2 결과 (dev 37건):** gemini-2.5-flash-lite 16 → **18/37**(필드 91%, 되묻기 오류 0), gpt-4.1-nano 2 → **13/37**(되묻기 오류 31 → 2), gpt-5-nano 6/37. 되묻기를 코드로 옮긴 효과가 가장 컸다.
- **v2 남은 오답 (Gemini):**
  - **달력을 줘도 "다음주 X요일"을 이번 주 X요일로 계산했다**(d11, d22, d29, m06).
  - **이미 표현한 조건을 `unhandled`에 중복으로 넣었다**(8건, 규칙을 추가했는데도).
  - 인원 계산 실수(d06, d10, d15), 특정 날짜를 기간으로 바꿈(d18, m04).
  - 무료 등급의 작은 모델이 가진 한계로 보인다.

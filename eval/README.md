# 평가셋

`cases.json`의 각 케이스는 `입력 문장 → 정답 조건(SearchConditions)`이다. 스키마는 `src/lib/schema.ts`.

- **dev:** 프롬프트를 고칠 때 보는 케이스.
- **holdout:** 프롬프트 개선 중에는 **보지 않고**, 마지막에 한 번만 측정한다. dev에 과적합한 수치를 걸러내기 위한 것이다.
- 정답 라벨은 AI가 초안을 쓰고 **사람이 전부 검수**한다. 수정한 라벨은 `docs/ai-log.md`에 남긴다.
- 검수하기 쉽도록 `expected`에는 **값이 있는 필드만** 적는다. 나머지는 로더(`eval/cases.ts`)가 `null`/`[]`로 채운다.
- `npm run eval:check`는 스키마를 검증하고, 검수용으로 케이스마다 날짜의 요일을 함께 출력한다.

## 해석 규칙

정답 라벨과 프롬프트가 모두 이 규칙을 따른다. 규칙을 바꾸면 라벨도 다시 검수한다.

### 공통
- 언급되지 않은 조건은 `null`(배열은 `[]`)이다. 사이트 기본값(2명 등)을 채우지 않는다.
- 스키마로 표현할 수 없는 조건은 버리지 않고 원문 그대로 `unhandled`에 넣는다(예: "주차 무료", "조용한 곳", "조식"). 채점은 비었는지 여부만 본다.

### 날짜 (모든 케이스는 `referenceDate`를 기준으로 해석)
- 한 주는 **월요일~일요일**이다. "이번주"는 referenceDate가 속한 주, "다음주"는 그다음 주다.
  - 예: referenceDate 2026-10-13(화) → 이번주 금 = 10/16, 다음주 금 = 10/23
- "금토", "목~토"처럼 요일 두 개는 **체크인 요일~체크아웃 요일**이다. 사이트 날짜 표기(`01월 21일(목) - 01월 23일(토)`)와 같다. "금토" = 금 체크인, 토 체크아웃, 1박.
- "오늘"은 referenceDate, "내일"은 그다음 날이다.
- "주말"만 있으면 **토요일 체크인 1박**이다. "이번 주말"은 referenceDate가 토·일이면 그 주의 토요일이고, 이미 지났으면 다음 토요일이다.
- 연도 없는 날짜("12월 24일")는 referenceDate 이후 가장 가까운 날짜다.
- 체크인만 있고 박수가 있으면 체크아웃을 계산한다("24일부터 2박" → 24~26).
- 체크인만 있고 박수가 없으면 **1박**으로 본다.
- "N월 첫째 주말"은 그 달의 첫 토요일 체크인 1박이다. "11월 첫째주 주말" → 11/7(토)~11/8.

#### 기간으로 말한 경우 (`dateRange`, `nights`, `weekend`)
고객은 정확한 날짜보다 기간으로 말하는 경우가 많다(사람이 쓴 holdout u01~u05 중 4건). 이때는 되묻지 않고 **기간 안에서 빈 방을 찾는다.**
- 날짜가 특정되면 `checkIn/checkOut`만 쓰고 `dateRange/nights/weekend`는 `null`이다. 둘을 같이 쓰지 않는다.
- `dateRange`는 **체크인할 수 있는 날짜의 범위**다(양 끝 포함).
  - "N월", "N월 중", "N월에" → N월 1일~말일
  - "N월 초" → 1~10일, "N월 중순" → 11~20일, "N월 말" → 21일~말일
  - "연말" → 12월 21~31일 ("12월 말"과 같다)
  - "다음달" → referenceDate 다음 달 1일~말일
- `nights`: "3박" → 3, "2박3일", "3일" → 2, "한 달" → 30. 언급이 없으면 `null`이다(검색은 1박으로 찾는다).
- `weekend`: 기간과 함께 "주말", "주말 포함"이라고 하면 `true`다. 토요일 숙박이 포함되어야 한다는 뜻이다.
- 박수만 있고 기간이 없으면(`"한 달 살기 할 곳"`) `nights`는 채우고 날짜는 되묻는다.

#### 날짜 되묻기
- 특정 날짜도 기간도 없을 때만 `needsClarification`에 `"dates"`를 넣는다("숙소 추천해주세요", "휴가 때").

### 인원
- `guests`는 **인원수에 포함되는 사람**만 센다. 36개월 이하 영유아는 `infants`로 따로 센다(사이트 이용규정 기준, `docs/evidence/03`).
- "아기", "돌", "N개월(36 이하)", "신생아"는 영유아다.
- "아이", "N살", "초등학생"은 인원에 포함한다. 나이가 애매하면 **포함하는 쪽**으로 해석한다. 정원보다 적게 세면 입실 거부로 이어지지만, 많이 세면 선택지만 줄어든다.
- "가족 4명"처럼 구성 없이 숫자만 있으면 모두 `guests`다.
- 인원 언급이 아예 없거나 셀 수 없으면("가족끼리", "친구들이랑") `guests = null`, `needsClarification`에 `"guests"`를 넣는다.
- "N명이서", "셋이서"는 본인을 포함한 총인원이다. "커플", "둘이"는 2명이다.
- 사람이 아닌 동반자는 세지 않는다: "강아지랑 둘이" = 1명 + 반려동물.
- "부모님 모시고"는 최소 3명이지만 정확한 수가 아니므로 `guests = null`, 되묻는다.

### 지역
- `region`은 사이트 지역 8개 중 하나다. "속초", "양양" → 강원, "해운대" → 부산, "송도" → 인천, "강남" → 서울.
- `area`는 사용자가 시·구·동네를 말했을 때만 채운다. 접미사는 뺀다("속초시" → "속초").
- 지역 언급이 없으면 `region = null`이다. 전 지역을 검색하면 되므로 되묻지 않는다.
- 8개 지역에 없는 곳("경주")은 `region = null`, 원문을 `unhandled`에 넣는다. 응답에서 "운영하지 않는 지역"이라고 안내할 근거가 된다.
- 역·해변 같은 랜드마크("부산역 근처")는 `area`가 아니라 `unhandled`다.

### 객실 조건
- `pet`: 반려동물을 데려가면 `true`. "강아지 맡기고 가요"처럼 데려가지 않으면 `null`.
- `oceanView`: "바다 보이는", "오션뷰"면 `true`. "바다 근처", "해변 가까운"은 위치 조건이므로 `unhandled`에 넣는다.
- `minBedrooms`: "방 2개", "투룸" → 2. "방 따로"만 있고 숫자가 없으면 2. "세 커플", "두 가족"처럼 일행이 여러 팀이면 팀 수만큼 방이 필요하다고 본다("세 커플" → 3).
- `minBeds`: 침대 수를 명시하거나 규칙으로 계산할 수 있을 때만 채운다.
  - "침대 2개" → 2
  - "다 따로 자야 해요", "각자 침대" → `guests`
  - "아이 침대 따로" → 2 (어른 침대 1 + 아이 침대 1)
- `features`: 욕조 → `bathtub`, 스파·월풀 → `spa`, 트윈·싱글 두 개 → `twin`, 휠체어·베리어프리 → `barrierFree`, 복층 → `loft`, 커넥팅·옆방 연결 → `connecting`.
- `facilities`: 주방·요리 → `kitchen`, 세탁기·빨래 → `washer`, 식기세척기 → `dishwasher`, 책상·재택·업무 → `desk`, 스타일러 → `styler`.

### 되묻기 (`needsClarification`)
- 날짜와 인원만 되묻는다. 이 둘이 없으면 재고와 정원을 확인할 수 없기 때문이다.
- 다른 조건은 없으면 없는 대로 검색한다.

## 채점
- 필드별 정확 일치. 배열은 순서를 무시한 집합 비교. `unhandled`는 비었는지 여부만 비교한다.
- 케이스 정답률: 모든 필드가 맞은 케이스의 비율.
- 되묻기 정확도: `needsClarification`이 정확히 맞은 케이스의 비율. 물어야 할 때 안 물었는지, 안 물어도 될 때 물었는지 따로 센다.
